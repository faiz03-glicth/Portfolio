# Architecture

This document records _why_ the system is shaped the way it is, including the
options that were rejected. It is written to be useful to whoever picks this up
later — including me, in a year.

## 2. Why Next.js

A portfolio is mostly **content that should be fast and indexable**, with a few
pockets of interactivity and a handful of server-side API calls that must hold
secrets.

Next.js covers all three in one runtime:

- Server Components render content without shipping the data-fetching code to
  the browser. The homepage ships ~103 kB of shared JS despite having eight
  content sections.
- Route Handlers give a server-side place to hold tokens. A Spotify refresh
  token cannot live in a static site; it also does not justify a second service.
- Built-in metadata, sitemap, robots and OG image generation remove a category
  of hand-maintained files that go stale.

**Rejected:** a static site generator (Astro/Hugo) — no server to hold secrets,
so the Spotify and GitHub integrations would have to expose tokens client-side
or be dropped. A SPA — worse SEO and worse first paint for content that is
fundamentally documents.

## 3. Why a Modular Monolith

The system has one user (me), one deployment target, and traffic that will not
trouble a single small VPS. Splitting it would add network hops, deployment
coordination and failure modes in exchange for nothing.

What _is_ worth keeping is the **module boundaries**, so the seams exist if they
are ever needed:

```
UI Components        know only normalised domain models
      ↓
Services             compose, cache, decide fallbacks
      ↓
Repositories         Supabase access, one per aggregate
Adapters             one per external provider
      ↓
Providers            Postgres, Spotify, GitHub, GitLab
```

A component importing the Supabase client or calling `api.github.com` directly
is an architectural defect, not a shortcut.

### 3.1 Why not microservices

There is no requirement that microservices would satisfy here. None of the
usual triggers are present: no independent scaling need, no separate deployment
cadence, no team boundaries, no differing runtime requirements, no security
isolation requirement.

Adopting them anyway would mean operating a service mesh, distributed tracing
and multiple deploy pipelines for a personal site. That cost is real and the
benefit is zero.

See section 10 for the conditions that _would_ change this answer.

## 4. The Theme Architecture

### Decision: `theme.ts` is authoritative; nothing else defines visual values

The failure mode this avoids is familiar — a colour defined in a Tailwind
config, again in a CSS variable, again as a hex literal in three components,
and no way to change it confidently.

```
src/config/theme.ts
        │
        ├──► tailwind.config.ts        utility class names
        └──► src/styles/theme-css.ts   CSS custom properties
```

Only **colours** become runtime CSS variables, because colours are the one
token group that changes after build time (light to dark). Radii, motion curves
and the type scale are resolved statically by Tailwind — putting them in CSS as
well would be a second copy waiting to drift.

### Decision: Tailwind v3, not v4

Tailwind v4 moves design tokens into CSS `@theme` blocks. That is a good design
in general, but it conflicts with the requirement above: a `.ts` file cannot be
imported by a stylesheet, so tokens would either be duplicated in CSS or
generated by a build step that can silently go stale in development.

Tailwind v3's `tailwind.config.ts` imports `theme.ts` directly. One file, no
codegen, no drift. The cost is running one major version behind; the benefit is
that the single-source-of-truth requirement is actually enforced rather than
merely intended.

### Colours as HSL channels

Tokens are stored as `"222 24% 5%"`, not `"hsl(222 24% 5%)"` or `"#0a0d12"`.
Tailwind then composes them as `hsl(var(--color-primary) / <alpha-value>)`,
which makes `bg-primary/20`, `border-border/60` and similar work for _every_
token without declaring opacity variants by hand.

### No flash of wrong theme

A blocking inline script in `<head>` resolves stored preference, then OS
preference, then the configured default, and writes `data-theme` before first
paint. The CSS media query remains as the no-JavaScript fallback.

## 5. Configuration Separation

Three files, three questions, no overlap:

| File              | Answers                                                      |
| ----------------- | ------------------------------------------------------------ |
| `config/theme.ts` | What does it look like?                                      |
| `config/site.ts`  | Who does it belong to, and how does it describe itself?      |
| `config/app.ts`   | How does it run — environment, feature flags, cache windows? |

Mixing these is how a site name ends up hardcoded in a component and a cache
duration ends up in a stylesheet.

## 6. Database Architecture

Supabase (managed PostgreSQL), free tier. Setup, schema and verification steps
are in [`database.md`](database.md).

- Access goes through **repositories** — one per aggregate. Components never
  import the Supabase client.
- Two clients: an anon-key client for public reads, and a service-role client
  that exists **only** in server-side modules. The service key is never
  referenced from a file that can reach the browser bundle.
- Row Level Security is enabled on every table. Public content is readable by
  `anon`; everything else requires the service role.
- Schema changes are SQL migration files in version control, not console edits,
  so the schema can be rebuilt from scratch and verified in CI.

## 7. Integration Architecture

_(Implemented on the `integration` branch.)_

Every provider gets the same four-file shape:

```
lib/integrations/<provider>/
├── client.ts    transport: auth, base URL, timeouts, errors to Result
├── mapper.ts    vendor payload to normalised domain model
├── service.ts   caching, fallbacks, the public surface
└── types.ts     the vendor's shapes, kept out of the rest of the app
```

```
Provider → Adapter → Normalised Model → Service → UI
```

The UI consumes `Project`, `CodeActivity` and `RecentlyPlayedTrack`. It never
sees a GitHub or GitLab response shape. This is what makes `CodeActivityPanel`
identical for both forges, and it means adding a third provider is a new
directory rather than a component rewrite.

`ProjectService` composes database projects with GitHub and GitLab repositories
into one list. Callers ask for projects; they do not ask a specific provider
for repositories.

### Failure isolation

Adapters return `Result<T>` instead of throwing. A caller cannot reach `.data`
without narrowing on `ok` first, which makes handling failure structural rather
than a matter of remembering to.

```
Spotify down   →  that card shows "Spotify unavailable"  →  page is fine
GitHub down    →  that card falls back to cached data    →  page is fine
Supabase down  →  static content renders                 →  page is fine
```

### Caching

Windows are declared in `config/app.ts` and chosen per data class, not
uniformly:

| Data              | Window | Why                                         |
| ----------------- | ------ | ------------------------------------------- |
| Portfolio content | 1 hour | Changes when I change it                    |
| Repositories      | 30 min | Changes slowly, rate limits matter          |
| Recently played   | 60 s   | Changes fast; still must not hammer Spotify |

## 8. Security Architecture

- **Secrets are server-only.** Only `NEXT_PUBLIC_`-prefixed variables reach the
  browser. Tokens are read inside modules that are never imported by a Client
  Component.
- **Least privilege.** Public GitHub/GitLab data needs no token, or a read-only
  one. Spotify uses a refresh token scoped to `user-read-recently-played`.
- **Errors are sanitised.** `Result.error` carries a fixed code and a message
  written for a visitor. Upstream bodies, URLs with credentials and stack
  traces never reach the client. The route-level error boundary shows a digest,
  not `error.message`.
- **Security headers** are set in `next.config.mjs`: `nosniff`, `DENY` framing,
  a constrained `Referrer-Policy`, and a `Permissions-Policy` that turns off
  camera, microphone and geolocation.
- **Non-production is `noindex`.** A staging copy outranking the real site is a
  genuinely annoying problem to undo.

## 9. Deployment Architecture

Target: **Hostinger VPS** — Node.js, PM2, Nginx.

Next.js needs a Node runtime for Server Components, Route Handlers, ISR and
image optimisation. Hostinger's shared hosting cannot provide that, and a
static export would mean deleting the integration layer. A VPS is the smallest
environment that actually runs this application.

`output: "standalone"` emits a self-contained server bundle, so the machine
does not need a full dependency install or a build toolchain.

```
Developer → GitLab → Merge Request → CI (lint, types, tests, build)
                                        ↓
                                      main
                                        ↓
                              rsync over SSH → VPS
                                        ↓
                            PM2 reload (zero downtime)
                                        ↓
                          Nginx reverse proxy + HTTPS
```

Credentials live in GitLab protected CI/CD variables. Nothing is hardcoded.

The application stays portable: nothing depends on a Hostinger-specific API, so
Vercel, Fly, Railway or a different VPS would work with a different deploy job
and no application changes.

## 10. When to Break This Apart

The modular monolith is correct _for now_. It stops being correct when one of
these becomes true:

| Trigger                                     | Why it changes the answer                                          |
| ------------------------------------------- | ------------------------------------------------------------------ |
| Background processing becomes substantial   | Long-running jobs should not share a process with request handling |
| One integration needs independent scaling   | Coupled scaling wastes resources or throttles the site             |
| A second application consumes the same data | A shared service beats duplicating the integration layer           |
| Asynchronous workloads appear               | Queues and workers want their own lifecycle                        |
| A component needs a different runtime       | For example, a Python ML step                                      |
| Security isolation becomes necessary        | Handling third-party data that must not share a process            |
| Deployment independence becomes valuable    | When releasing one part should not risk the rest                   |

Until then, extracting a service would be paying operational cost for an
architecture diagram.

### What extraction would look like

Because the seams already exist, extraction is mechanical rather than a
rewrite: an adapter directory becomes a service, and `service.ts` becomes an
HTTP client against it. The normalised models and every component stay
unchanged — which is the entire point of maintaining the boundary while it is
still cheap to do so.

---

## 11. Future Integrations

Adding LinkedIn, LeetCode, Steam, YouTube, Discord, Dev.to or Medium means:

1. `src/lib/integrations/<provider>/` with the four-file shape
2. A mapper into an existing normalised model, or a new one in `lib/types/`
3. A feature flag in `config/app.ts`
4. Reuse of `IntegrationCard` for the four render states

No component, no page and no theme value should need to change.

> Roblox is explicitly **not** implemented in this version.
